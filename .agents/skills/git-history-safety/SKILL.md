# Git 历史与恢复安全

## 基本原则

- 操作前检查工作区、当前分支、远程跟踪关系和相关提交历史；优先选择可撤销、不会重写共享历史的方案。
- 分支管理（`main` 仅用户操作 / `dev` 禁止直接提交功能与修复但允许维护仓库类 / 功能·修复基于 `dev` 建分支走 PR/MR）以 AGENTS.md「分支管理」为唯一准绳。
- 任何可能丢失未提交内容、删除文件、覆盖远程或重写历史的操作，都必须先说明影响并获得用户明确确认。

## Merge 与 Rebase

- 公共分支或已推送、多人协作的分支禁止 rebase；本地且未推送的个人功能分支才可使用 rebase 整理历史。
- 同步共享分支优先 merge；功能分支合回 `dev` 时优先通过 PR/MR，并按仓库策略决定是否 `--no-ff`。
- 禁止在 `main`/`master` 上强制推送。其他分支也仅在用户明确要求、确认影响后执行；可行时优先 `--force-with-lease`。
- 遇到冲突时先列出冲突文件和双方改动意图，给出保留或整合建议；不要盲选某一侧，也不要未分析就 `--skip`、`--abort` 或继续操作。

## 恢复顺序

按损失从小到大选择方案：

1. 查看 `git diff`、`git status`、`git log` 和 `git reflog`，确认内容是否仍可恢复。
2. 用新分支、临时 commit 或 stash 保护当前工作，再尝试 `restore`、`revert` 或检出单个文件。
3. 仅需撤销已发布提交时优先 `git revert`，避免改写共享历史。
4. `git reset --hard` 会丢弃未提交改动；执行前必须确认目标 commit 并再次征得同意。
5. `git clean -fd` 会删除未跟踪文件；必须先用 dry-run 列出将删除的内容并确认。

- 不使用硬重置覆盖多人协作分支，不把 `reflog + reset --hard` 作为首选恢复方案。
- 操作完成后重新检查状态与历史，并明确说明保留、删除或重写了什么。
